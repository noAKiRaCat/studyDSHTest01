# Deep Agents 03 · 子代理与上下文工程

> 长任务的核心矛盾：**要做的事很多，上下文窗口很小**。解法只有两个——隔离与压缩。

---

## 1. 子代理（Subagents）

### 1.1 为什么需要

主代理如果亲自做所有事，上下文会被：
- 中间搜索结果
- 大段文件内容
- 失败重试的噪声

迅速填满。子代理把这些脏活塞进独立上下文，只回传结论。

```text
主代理上下文：任务 + 子代理结论（干净）
子代理上下文：搜索过程 + 原始资料（脏，用完即弃）
```

### 1.2 内置 `task` 工具

开启后，主代理可以这样用：

```text
task(name="researcher", description="调研 2026 年 LLM Agent 框架格局")
```

返回一份报告字符串。

### 1.3 自定义子代理

```python
from deepagents import create_deep_agent

agent = create_deep_agent(
    model="openai:gpt-5.5",
    tools=[search, read_pdf, run_python],
    subagents=[
        {
            "name": "researcher",
            "description": "负责网络/文档调研，返回带引用的摘要",
            "system_prompt": "你是研究员。用 search 与 read_pdf 收集资料，"
                             "输出带出处的要点列表，不要臆造。",
            "tools": [search, read_pdf],
            "model": "anthropic:claude-sonnet-5",
        },
        {
            "name": "coder",
            "description": "负责写代码与运行分析脚本",
            "system_prompt": "你是数据分析师。用 run_python 处理数据并给出结论。",
            "tools": [run_python],
            "model": "openai:gpt-5.5",
        },
    ],
)
```

**要点**：

- `description` 是主代理选人的唯一依据，写清「什么时候用我」。
- 子代理可以用不同模型（省钱/提速）。
- 子代理的工具应是父代理工具的子集或专用集合。

### 1.4 上下文模式

| 模式 | 行为 | 适用 |
|---|---|---|
| `isolated`（默认） | 全新上下文，只看任务描述 | 独立调研、互不干扰 |
| `fork` | 继承父代理全部历史 | 需要「接着刚才的话说」 |

```python
{"name": "editor", "description": "...", "mode": "fork"}
```

### 1.5 异步子代理

需要长时间后台跑时：

```python
agent = create_deep_agent(
    model="openai:gpt-5.5",
    async_subagents=True,   # 概念性开关，具体参数见官方 API
)
```

主代理获得 `launch` / `check` / `update` / `cancel` 四个工具，可以先启动、稍后取结果、中途调整指令。

### 1.6 关闭子代理

不需要 `task` 时（例如只做单线程任务），在 harness profile 中排除该工具。

## 2. 上下文工程

### 2.1 四层结构

```text
① 输入上下文   系统提示 + 记忆 + 技能 + 工具说明
② 压缩        历史摘要 + 大结果卸载到文件
③ 隔离        子代理吞掉重活，只回结论
④ 长期记忆    跨会话保留的事实与偏好
```

### 2.2 压缩（Summarization）

当历史超过阈值，框架自动把早期对话压缩成摘要，保留最近若干条原文。

可调参数（中间件形式）：

```python
from deepagents import create_deep_agent
from langchain.agents.middleware import SummarizationMiddleware

agent = create_deep_agent(
    model="openai:gpt-5.5",
    middleware=[SummarizationMiddleware(max_tokens=8000, keep_last=10)],
)
```

### 2.3 卸载（Offloading）

工具返回超长结果时，写入虚拟文件，上下文里只留「已保存到 /tmp/result_1.json，共 3 万行」这类指针。需要时 Agent 再 `grep` 或 `read_file` 局部读取。

这比「全部截断」好得多：信息没丢，只是不占上下文。

### 2.4 实践建议

| 做法 | 收益 |
|---|---|
| 大文件分块读（`offset`/`limit`） | 避免一次性撑爆 |
| 用 `grep` 定位再 `read_file` 精读 | 减少无关内容 |
| 中间结果写文件而不是堆在消息里 | 上下文可控 |
| 子代理返回「结论 + 文件路径」 | 主代理按需取细节 |
| `AGENTS.md` 只写稳定规则 | 每轮都加载，越短越好 |

## 3. 技能（Skills）

### 3.1 结构

```text
skills/
└── weekly-report/
    ├── SKILL.md          # 必需：frontmatter + 使用说明
    ├── template.docx
    └── references/
        └── style-guide.md
```

`SKILL.md`：

```markdown
---
name: weekly-report
description: 生成周报：读取数据 → 画图 → 填充模板 → 导出 PDF
---

# 步骤
1. `read_file /out/data.csv`
2. 调用 `make_chart` 生成趋势图
3. 用 `template.docx` 填充
4. `write_file /out/weekly.pdf`

# 注意
- 数字必须来自 data.csv，不得编造
- 图表标题使用中文
```

### 3.2 渐进式披露

启动时只加载 frontmatter（几十个 token），**任务命中时才读全文**。这样几十个技能也不会撑爆上下文。

### 3.3 与提示词的区别

| | 系统提示 | 技能 |
|---|---|---|
| 加载时机 | 每轮都加载 | 按需 |
| 适合内容 | 通用规则 | 特定任务的详细流程 |
| 体积 | 越小越好 | 可以长 |

## 4. 记忆（Memory）

`AGENTS.md` —— 始终加载的项目约定：

```markdown
# 项目约定
- Python 3.12，使用 uv 管理依赖
- 测试用 pytest，覆盖率不低于 80%
- 提交信息用中文，格式 `类型: 描述`
- 不要修改 migrations/ 下的历史文件
```

```python
agent = create_deep_agent(
    model="openai:gpt-5.5",
    memory=["./AGENTS.md"],
)
```

Agent 也可以在运行中**更新记忆**（写回 AGENTS.md），让偏好沉淀到下一次会话。

## 5. 委派策略设计

### 5.1 什么时候派子代理

| 适合 | 不适合 |
|---|---|
| 子任务步骤多、中间产物大 | 一句话就能答的 |
| 需要专用工具/模型 | 需要和用户反复确认的 |
| 可并行的独立调研 | 强依赖主上下文的细活 |

### 5.2 分工模式

```text
研究型：  planner → researcher × N → writer → reviewer
编码型：  architect → coder → tester → reviewer
分析型：  loader → analyst → visualizer → reporter
```

### 5.3 反模式

- **过度委派**：每个小步骤都派子代理，握手成本高于收益。
- **描述含糊**：主代理选错人。
- **子代理无边界**：没有明确交付物，返回一堆废话。
- **递归委派**：子代理再派子代理，成本失控（要显式限制深度）。

## 6. 常见坑

| 现象 | 原因 | 解决 |
|---|---|---|
| 子代理答非所问 | `description` 太笼统 | 写清触发条件与产出格式 |
| 主代理上下文仍爆 | 子代理返回全文而非摘要 | 在子代理提示里要求「只回结论 + 文件路径」 |
| 技能不生效 | 目录结构不对 / 缺 frontmatter | 按 `SKILL.md` 规范组织 |
| 记忆每轮太长 | `AGENTS.md` 写成了手册 | 只留稳定规则，细节放技能 |
