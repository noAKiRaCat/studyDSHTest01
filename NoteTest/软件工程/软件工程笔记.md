# 软件工程笔记

> 按软件生命周期组织：需求 → 设计 → 实现 → 测试 → 维护 → 管理 → 演进。
> 软工的核心不是背模型，而是回答一个问题：**怎么在有限成本下交付可维护的软件**。

---

## 第 1 章 软件工程概述与过程模型

### 基本概念

- 软件 = 程序 + 数据 + 文档。
- 软件危机的表现：进度失控、成本超支、质量不可靠、维护困难。
- 软件工程三要素：方法、工具、过程。

### 生命周期模型

| 模型 | 特点 | 适用 |
| --- | --- | --- |
| 瀑布 | 阶段严格串行，文档驱动 | 需求稳定、合同型项目 |
| 原型 | 先做可运行原型确认需求 | 需求不明确 |
| 增量 | 分批交付可用版本 | 需要尽早见效 |
| 螺旋 | 风险驱动，每圈含风险分析 | 大型高风险项目 |
| 敏捷 | 迭代 + 快速反馈 + 拥抱变化 | 需求频繁变动 |
| DevOps | 开发运维一体，持续交付 | 互联网产品 |

### 关键结论

- 模型没有优劣，只有是否匹配**需求不确定性**和**交付节奏**。
- 越晚发现的缺陷修复成本越高（指数级上升），所以要把质量左移。

## 第 2 章 需求工程

- 需求分两类：**功能需求**（做什么）、**非功能需求**（做得多好：性能、安全、可用性）。
- 需求获取方法：访谈、问卷、观察、原型、文档分析、联合应用设计（JAD）。
- 需求分析产出：数据流图（DFD）、用例图、状态图、数据字典。
- 需求规格说明书（SRS）应满足：完整、一致、无歧义、可验证、可追踪。
- 需求变更要管控：变更申请 → 影响分析 → 评审 → 更新基线。
- **用户故事**格式：作为〈角色〉，我想要〈功能〉，以便〈价值〉；配合验收标准。

### 易错点

- 把「解决方案」当需求写（「需要 Redis 缓存」是方案，「首页 1 秒内加载」才是需求）。
- 非功能需求没有量化指标，最后无法验收。

## 第 3 章 软件设计

### 设计原则

- **高内聚、低耦合**：模块内部职责单一，模块之间依赖少。
- SOLID：
  - 单一职责（SRP）
  - 开闭原则（OCP）：对扩展开放、对修改关闭
  - 里氏替换（LSP）
  - 接口隔离（ISP）
  - 依赖倒置（DIP）：依赖抽象而非实现
- 其他：DRY（避免重复）、KISS（简单优先）、YAGNI（不要过度设计）。

### 架构风格

| 风格 | 说明 | 代价 |
| --- | --- | --- |
| 分层 | 表现/业务/数据分离 | 层间穿透可能变多 |
| MVC / MVVM | 关注点分离 | 简单页面可能过度设计 |
| 微服务 | 独立部署、独立扩展 | 分布式复杂度、运维成本 |
| 事件驱动 | 异步解耦 | 最终一致性、调试困难 |
| 单体 | 简单、事务清晰 | 规模化后耦合严重 |

### 详细设计工具

- 类图、时序图、活动图、状态机图。
- 设计模式（常用）：工厂、单例、策略、观察者、装饰器、适配器、模板方法。
- 设计模式是「可复用的沟通词汇」，不是目标本身；滥用比不用更糟。

## 第 4 章 实现与编码规范

- 命名：见名知意，避免缩写歧义；常量全大写，类名大驼峰。
- 函数：单一职责、参数不超过 3~4 个、避免超过 50 行。
- 注释写「为什么」，不写「是什么」；过期注释比没有注释更危险。
- 代码评审（Code Review）：看正确性、可读性、边界条件、测试覆盖，不看风格偏好。
- 版本控制：小步提交、清晰的 commit message、分支策略（Git Flow / Trunk-Based）。
- 技术债要显式记录并排期偿还，否则会复利。

## 第 5 章 软件测试

### 层次

- 单元测试：函数/类级别，快，开发者写。
- 集成测试：模块间接口与数据流。
- 系统测试：完整功能与非功能验证。
- 验收测试：对照需求，用户视角。

### 方法

- 黑盒：等价类划分、边界值分析、判定表、因果图、场景法。
- 白盒：语句覆盖、判定覆盖、条件覆盖、路径覆盖（覆盖率递增，成本也递增）。
- 灰盒：接口 + 内部逻辑结合。

### 关键指标

- 缺陷密度、缺陷发现率、测试覆盖率、逃逸缺陷率。
- 单元测试要遵循 **FIRST**：快、独立、可重复、自验证、及时。
- 回归测试应自动化；手工回归是长期成本黑洞。

### 易错点

- 覆盖率 100% 不代表没有 bug，只代表代码被执行过。
- 只测正常路径、不测异常与边界，是线上事故的主要来源。

## 第 6 章 维护与演化

- 维护四类：纠错性、适应性、完善性、预防性。
- 维护成本通常占生命周期总成本的 60% 以上。
- 可维护性取决于：可读性、模块化、文档、测试覆盖。
- 遗留系统改造策略：绞杀者模式（逐步替换）、防腐层、灰度迁移。
- 重构：不改变外部行为的前提下改善内部结构；重构必须有小步测试保护。

## 第 7 章 项目管理

### 估算与计划

- 估算方法：专家判断、类比、自下而上、三点估算、故事点 + 速率。
- 关键路径法（CPM）：决定项目最短工期的那条链路。
- 甘特图看进度，网络图看依赖。

### 风险与质量

- 风险管理：识别 → 分析（概率 × 影响）→ 应对（规避/转移/减轻/接受）→ 监控。
- 质量成本：预防成本、评估成本、内部失败成本、外部失败成本。
- 配置管理：版本控制、基线、变更控制、发布管理。

### 度量

- 进度偏差、成本偏差、缺陷趋势、代码复杂度、交付周期（Lead Time）。
- 不要用代码行数衡量生产力。

## 第 8 章 敏捷与 DevOps

### 敏捷

- 宣言四条：个体与互动 > 流程工具；可工作软件 > 详尽文档；客户合作 > 合同谈判；响应变化 > 遵循计划。
- Scrum：Product Backlog、Sprint、每日站会、评审会、回顾会；角色为 PO、SM、开发团队。
- 看板：限制在制品（WIP）、可视化流程、持续交付。
- 用户故事地图：把故事按用户旅程铺开，帮助排优先级。

### DevOps

- 核心：打破开发与运维的墙，自动化一切可自动化的环节。
- CI：每次提交自动构建 + 测试；CD：自动部署到预发/生产。
- 基础设施即代码（IaC）：环境可复制、可版本化。
- 可观测性三支柱：日志、指标、链路追踪。
- 发布策略：蓝绿、金丝雀、灰度、特性开关。

### 常见坑

- 敏捷不等于没有计划，而是计划更短、更频繁。
- 没有自动化测试的 CI 只是「自动构建」，不能叫持续集成。
